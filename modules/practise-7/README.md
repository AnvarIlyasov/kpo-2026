# Практика 7. Структурный паттерн Decorator и декларативное профилирование

## Цель

Расширить сервис отправки уведомлений из [практики 6](../practise-6/README.md), применив структурный паттерн **Decorator (Декоратор)** совместно с декларативным подходом:

- **Decorator (Декоратор)** — прозрачное добавление сквозной функциональности (логирование и замер времени выполнения с отправкой в метрики) поверх отправителя `NotificationSender` без изменения его кода.
- **Декларативная разметка (аннотации / атрибуты / метаданные)** — управление включением декоратора через декларативную конфигурацию (аннотацию/атрибут целевого класса или метода), а не только ручным оборачиванием в коде.

---

## Контекст

В практике 6 появился отправитель сообщений:

```text
NotificationSender.send(notification) -> AttemptResult
```

В реальных распределённых системах критически важно отслеживать надёжность и задержки (latency) внешних вызовов. Если почтовый сервис или push-шлюз начинает отвечать медленно, это влияет на время обработки очередей доставки.

Мы хотим решить две задачи:
1. **Логирование вызовов**: фиксировать факт начала операции, параметры (канал, получатель), результат (`AttemptResult`) и общее затраченное время.
2. **Метрики задержки (Latency Metrics)**: передавать измеренное время выполнения в реестр метрик (например, для мониторинга в Grafana/Prometheus).

При этом базовый отправитель (`InMemoryNotificationSender`, реальный почтовый клиент или mock) не должен ничего знать ни о логах, ни о замерах времени, ни о таймерах (соблюдение Single Responsibility Principle). Добавление этой функциональности должно производиться через декоратор, а решение о его подключении — приниматься декларативно.

## Часть 1. Структурный паттерн Decorator

### 1. Контракт сборщика метрик времени

Выделите простой абстрактный контракт для фиксации метрик выполнения:

```text
ExecutionMetrics:
    recordExecution(operationName: String, duration: Duration, success: boolean)
```

Реализуйте тестовый накопитель метрик в памяти (`InMemoryExecutionMetrics`), который позволяет:
- получить список всех зарегистрированных замеров;
- узнать суммарное или среднее время выполнения по имени операции;
- узнать число успешных и неуспешных выполнений.

### 2. Реализация декоратора `TimedLoggingSenderDecorator`

**Обязанности декоратора:**
1. Засекает начальный момент времени (через абстракцию таймера/часов, чтобы тесты не зависели от `Thread.sleep` и системных пауз).
2. Вызывает метод `send(notification)` у целевого отправителя (`target`).
3. Засекает конечное время и вычисляет затраченную длительность (`duration`).
4. Формирует запись лога:
   - идентификатор или тип операции (например, `"NotificationSender.send"`);
   - канал и получатель уведомления;
   - статус (`SUCCESS`, `TEMPORARY_FAILURE`, `PERMANENT_FAILURE`);
   - затраченное время.
5. Передаёт замер в `ExecutionMetrics.recordExecution(...)`.
6. Если целевой отправитель выбросил исключение:
   - фиксирует затраченное время до момента сбоя;
   - передаёт в метрики факт неуспешного вызова (`success = false`);
   - записывает ошибку в лог;
   - пробрасывает исходное исключение дальше без проглатывания.
7. Возвращает неизменённый результат `AttemptResult`.

## Часть 2. Декларативная разметка (Аннотация / Атрибут / Спецификация)

Сделайте так, чтобы декоратор можно было подключить **декларативно**, разметив целевой класс или метод.

### Требования к разметке:
1. Создайте аннотацию / атрибут (например, `@TimedExecution` или `@LogAndProfile`):
   - возможность указать имя метрики/операции (например, `operation = "notification.send"`);
   - флаг логирования (например, `boolean logDetails() default true`).

### Конфигуратор / Фабрика обёртки:
Создайте механизм (фабрику, конфигуратор или прокси-генератор), который принимает исходный `NotificationSender`:
- Если класс/метод помечен аннотацией / метаданными профилирования: возвращается объект, обёрнутый в декоратор с заданными параметрами.
- Если разметки нет: возвращается исходный объект без накладных расходов.

Пример использования в псевдокоде:

```text
@TimedExecution(operation = "email.delivery")
class FastEmailSender implements NotificationSender { ... }

rawSender = new FastEmailSender()
sender = SenderProfiler.wrapIfNeeded(rawSender, metrics, logger, timeSource)
// sender теперь прозрачно логирует вызовы и пишет в metrics!
```

Для языков без рантайм-аннотаций методов (например, Go):
- Используется декларативная конфигурационная структура (pipeline/options) или структура со спецификацией тегов:
```go
type SenderProfileSpec struct {
    Operation  string
    LogDetails bool
}

sender := profiler.WrapWithProfile(rawSender, spec, metrics, logger, clock)
```

## Часть 3. Интеграция с сервисом доставки из Практики 6

Покажите бесшовную интеграцию декоратора с кодом предыдущей практики:

1. Создать уведомление через Builder и Factory из практики 5.
2. Создать отправитель `InMemoryNotificationSender` с заданным результатом (например, с временной ошибкой, а затем успехом).
3. Через декоратор обернуть его в `TimedLoggingSenderDecorator`, подключив `InMemoryExecutionMetrics` и журнал логов.
4. Передать полученный декорированный `NotificationSender` в `DeliveryService` из практики 6.
5. Вызвать `processDue(now)`:
   - `DeliveryService` выполняет отправку штатным образом, не подозревая о наличии обёртки;
   - `RetryPolicy` принимает решения о повторах;
   - `DeliveryObserver` получает события попыток;
   - В `ExecutionMetrics` появляются точные записи о времени каждой попытки;
   - В логе аудита фиксируются факты вызовов с замером времени.

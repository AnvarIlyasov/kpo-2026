# ВышКат — Доедем до дедлайна

Домашнее задание №1: консольный учёт парка, SOLID, Spring DI и тесты.

## Сборка и запуск

Требуются **JDK 25**, доступ к Maven Central при первой сборке и терминал UTF-8.
Gradle 9.2.0 включён в проект через wrapper; отдельно устанавливать Gradle не нужно.
Spring Context 7.0.9 используется как DI-контейнер. Spring Boot, HTTP и база данных не нужны.
Исходники компилируются в Java 17 bytecode, но настроенная сборка и её запуск используют JDK 25.

В PowerShell из папки `HW-1`:


```powershell
# Если JAVA_HOME ещё не настроен, укажите каталог своего JDK 25:
chcp 65001
$env:JAVA_HOME = 'C:\Users\PC\.jdks\jdk-25.0.4.1+1'
.\gradlew.bat --console=plain clean check installDist
.\build\install\vyshkat\bin\vyshkat.bat
```

Путь JDK выше — пример для компьютера, на котором проверен проект. На другом компьютере замените его.
Альтернативный запуск: `.\gradlew.bat --console=plain run`.
На Linux/macOS используйте `sh ./gradlew clean check installDist`, затем
`./build/install/vyshkat/bin/vyshkat` с установленным JDK 25.

В IntelliJ IDEA откройте **папку HW-1 как отдельный проект**, импортируйте Gradle,
выберите JDK 25 для Project SDK и Gradle JVM. Запускайте класс
[`Main`](src/main/java/Main.java).
Корневые настройки учебного репозитория не изменяются: HW-1 имеет самостоятельный `settings.gradle.kts`.

`check` запускает тесты и проверяет покрытие строк всего production-кода не ниже 60%.
Отчёт тестов: `build/reports/tests/test/index.html`.
Покрытие: `build/reports/jacoco/test/html/index.html`.

Результаты актуального запуска тестов и покрытия доступны в отчётах выше.

## Пользовательский интерфейс и правила

Меню: 1 — добавить транспорт; 2 — добавить вещь; 3 — отчёт;
4 — транспорт для новичков; 5 — имущество; 0 — выход.
Данные вводятся интерактивно, никаких объектов для демонстрации в production-коде нет.
Всё хранится в памяти только до завершения процесса, при следующем запуске парк пуст.

- Электросамокат, велосипед и электровелосипед проходят техосмотр перед добавлением.
- Упрощённая модель техосмотра: оператор вводит наличие неисправности (да/нет),
  `BasicServiceCenter` отклоняет неисправный транспорт. Это не физическая диагностика.
- Отказ содержит причину, ничего не добавляет и не резервирует инвентарный номер.
- Шлемы и зарядные станции добавляются как вещи. Техосмотр вещей условием не задан.
- Инвентарный номер обязателен и уникален среди транспорта и вещей. Пробелы по краям
  удаляются, регистр значим: `B1` и `b1` — разные номера.
- Простота — целое число 1–10. Для новичков выбирается только принятый транспорт с оценкой ≥ 6.
- Суточный расход — неотрицательное десятичное число. Можно вводить точку или запятую.
  Допустимый диапазон: от 0 до 1 000 000 кВт·ч в сутки, точность — до 3 знаков
  после запятой (концевые нули не учитываются). Это выбранное ограничение приложения,
  а не требование ТЗ. Оно защищает суммирование и вывод от чрезмерно больших чисел
  и масштаба. Например, `1e2147483647` отклоняется; `1.23000` принимается.
  Для точного суммирования используется `BigDecimal`.
- Энергия парка трактуется как сумма энергии всех потребителей на балансе,
  включая зарядные станции. Их введённый расход считается отдельным расходом объекта:
  оператор не должен повторно записывать одну и ту же энергию зарядки в два объекта.
- Отчёт показывает отдельно транспорт, вещи и общее число объектов.
- При ошибке ввода операция отменяется и управление возвращается в меню.
  Завершение потока ввода, в том числе посреди добавления, корректно завершает приложение.

## Архитектура

Префикс `ru.hse.vyshkat` убран: `Main` и `AppConfig` лежат прямо в `src/main/java`.
Короткие пакеты `domain`, `service`, `console` разделяют код по назначению.
Тесты лежат в `src/test/java`.

`domain` содержит неизменяемые объекты и проверку допустимых значений:

- [`Inventoriable`](src/main/java/domain/Inventoriable.java) — имя и инвентарный номер;
- [`EnergyConsumer`](src/main/java/domain/EnergyConsumer.java) — суточная энергия;
- `Asset` → `Transport` → `Bicycle` или `ElectricTransport` → `ElectricScooter` / `ElectricBicycle`;
- `Asset` → `InventoryItem` → `Helmet` / `ChargingStation`.

`ElectricTransport` объединяет хранение расхода у двух электрических видов.
`InventoryItem` ограничивает метод добавления вещей: через него нельзя обойти техосмотр транспорта.
Велосипед и шлем не реализуют `EnergyConsumer` и не получают фиктивных энергетических методов.

[`FleetService`](src/main/java/service/FleetService.java) управляет приёмкой,
уникальностью номеров, хранением и отчётами. Возвращаемые списки неизменяемые.
Отдельный repository не введён: единственного хранилища в памяти достаточно.
[`ServiceCenter`](src/main/java/service/ServiceCenter.java) — заменяемое правило техосмотра.
[`ConsoleApp`](src/main/java/console/ConsoleApp.java) читает ввод, создаёт доменные
объекты и выводит ответы, но не решает, кого принять и кто подходит новичкам.

[`AppConfig`](src/main/java/AppConfig.java) объявляет Spring beans.
Spring передаёт `ServiceCenter` в фабричный метод `FleetService`, а сервис парка — в консоль.
`Main` открывает и закрывает контекст. Зависимости передаются через конструкторы;
доменные объекты не зависят от Spring и создаются при пользовательском вводе.

## SOLID и обязательные вопросы

**Наиболее явно применён DIP:** `FleetService` зависит от интерфейса `ServiceCenter`,
а не от `BasicServiceCenter`. Реализация выбирается в `AppConfig`, в тестах заменяется fake.

**SRP:** объекты проверяют собственные инварианты; техосмотр принимает решение;
сервис управляет балансом; консоль отвечает за ввод/вывод; конфигурация собирает зависимости.
Хранение и небольшие отчёты оставлены в одном сервисе как связанная задача учёта парка.

**OCP:** новый подкласс `Transport` принимается существующим сервисом; новый
`EnergyConsumer` участвует в сумме без проверки конкретных классов транспорта.
Тест `newTransportSubtypeNeedsNoFleetChanges` демонстрирует расширение.

**LSP:** конкретные виды сохраняют контракт `Transport` (простота 1–10, наличие
инвентарных данных), не отключают унаследованные операции. Электрические виды
сохраняют неотрицательность расхода. У объектов нет изменяемого состояния,
которое позволило бы нарушить эти инварианты после приёмки.

**ISP:** инвентаризация и энергопотребление — два небольших интерфейса.
Не потребляющие энергию объекты не обязаны реализовывать ненужный метод.

**Что сознательно ограничено:** OCP на уровне консольного создания объектов.
При добавлении вида транспорта нужно добавить пункт меню и ветку создания в `ConsoleApp`.
Это приемлемый компромисс: реестр плагинов и отдельная фабрика для каждого типа
усложнили бы приложение из трёх видов транспорта. Интерфейс самого `FleetService`
не выделен, поскольку независимых реализаций и потребности в их замене пока нет.

**Что произойдёт при расширении:**

- Новый транспорт: новый класс, при необходимости `EnergyConsumer`, и изменение
  меню создания. Техосмотр и отчёты сохраняются при прежних правилах.
  Если нужны особые критерии осмотра, потребуется изменить/заменить сервис техосмотра.
- Сотрудник: отдельная модель и сервис сотрудников. Сотрудник не наследует `Asset`
  и не попадает на баланс; существующий учёт имущества не меняется.
- Склад запчастей: отдельная модель остатков и складских операций. Штучный учёт
  парка нельзя автоматически считать количественным складским учётом.
- Постоянное хранение: потребуется выделить repository и заменить хранение внутри
  сервиса; текущая версия намеренно не обещает поддержку базы без изменений.

## Тестирование и подмена DI

[`FleetServiceTest`](src/test/java/FleetServiceTest.java):
`inspectionDecisionControlsAdmissionAndRejectedNumberCanBeReused` передаёт fake через
конструктор: первая проверка отклоняет, вторая принимает. Тест проверяет состояние
парка и число обращений. `beginnerThreshold` проверяет значения 1, 5, 6 и 10.
Также проверяются смешанная энергия, уникальность номеров, пустой парк,
неизменяемость отчётов и отсутствие изменений при исключении техосмотра.

[`SpringDiTest`](src/test/java/SpringDiTest.java):
`springInjectsReplacementInspectionIntoProductionFleetBean` регистрирует fake как
primary bean `ServiceCenter` в настоящем Spring-контексте с production `AppConfig`.
Тот же фабричный метод создаёт `FleetService`, но получает тестовый техосмотр,
отклоняющий исправный велосипед. Отдельный тест собирает обычную конфигурацию.

[`DomainTest`](src/test/java/DomainTest.java) проверяет инварианты.
[`ConsoleAppTest`](src/test/java/ConsoleAppTest.java) проверяет
пользовательский сценарий, ошибки и EOF через подменённые потоки, без запуска терминала.

## Демонстрация для проверки

Выполните действия вручную через меню. Значения ниже — инструкция для пользователя,
а не встроенные данные приложения.

| Шаг | Команда и ввод | Результат |
|---|---|---|
| 1 | 3, затем 4 и 5 | Нулевой отчёт и пустые списки |
| 2 | 1 → вид 1 → Самокат → S1 → 6 → нет → 1,2 | Принят |
| 3 | 1 → вид 2 → Велосипед → B1 → 5 → нет | Принят |
| 4 | 1 → вид 3 → Электровелосипед → E1 → 7 → нет → 0.3 | Принят |
| 5 | 1 → вид 1 → Неисправный → X1 → 10 → да → 8 | Отклонён |
| 6 | 2 → вид 1 → Шлем → H1 | Добавлен |
| 7 | 2 → вид 2 → Станция → C1 → 2.1 | Добавлена |
| 8 | 2 → вид 1 → Другой шлем → S1 | Ошибка повторного номера |
| 9 | 3 | Транспорт 3, вещи 2, всего 5; энергия 3.6 кВт·ч |
| 10 | 4 | Самокат S1 и электровелосипед E1 |
| 11 | 5 | Названия и номера пяти принятых объектов |
| 12 | Неизвестная команда; затем добавление с простотой abc | Сообщения об ошибке, меню продолжает работу |
| 13 | 0 | Выход |

После отказа можно повторно добавить исправный транспорт с номером X1;
после этого отчёты соответственно изменятся. Для демонстрации границ введите
простоту 0 или 11, отрицательную энергию и пустое имя — операции должны отклоняться.
